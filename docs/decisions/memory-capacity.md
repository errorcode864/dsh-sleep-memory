# 长记录与密集关联容量验证

E4 提供固定合成数据和独立子进程测试，覆盖索引、召回、重载及 v4 备份恢复。
本轮不增加索引依赖，不改召回算法，不进行模型请求或个人 profile 操作。

## 复现

在插件源码 checkout 中运行：

```sh
npm run bench:capacity -- --sizes 1000,10000,20000 --profiles short,long,dense --repeats 3 --timeout-seconds 240 --report tmp/capacity-memory-final.json
```

真实宿主模式先设置 `DSH_APP_PACKAGE` 为本机已安装的 `dsh/package.json` 路径：

```sh
npm run bench:capacity -- --backend disk --sizes 1000 --profiles short,long,dense --repeats 3 --timeout-seconds 240 --report tmp/capacity-disk.json
```

各组合在独立子进程顺序执行，默认最大堆为 3072 MiB；可用 `--heap-mib` 调整。
`--sizes` 支持 10～20000，`--repeats` 支持 1～10，每组合超时可设 5～900 秒。
超时只终止测试子进程，保留最近完成阶段及诊断；临时数据不会自动删除。
报告记录 Node、CPU、内存、Git 基线、参数、脚本 SHA-256、原始时间样本与数据校验摘要。

## 固定数据与口径

| 场景 | 每条正文 | 每条联想边 |
| --- | --- | --- |
| `short` | 160 字符 | 0 |
| `long` | 2000 字符 | 0 |
| `dense` | 600 字符 | 16 |

数据使用一个项目、固定时间、可定位的目标记录与环形同项目联想。
正文使用重复中文条件语句，不能代表长日志、多语种或大量唯一词的成本。
每组最多另带 1000 个叙述版本、200 条呈现记录及含 32 条前后快照的审计批次。
叙述包含四版本链及撤回状态，均为固定合成资料，不代表模型生成质量。

每组先测纯索引冷构建、复用构建和评分，再运行完整插件的预演、恢复、导出与召回。
召回区分首次和重复调用，断言目标命中、项目隔离、关联扩散与撤回历史不变。
内存模式使用严格 schema 与快照替身；重载包含 JSON 解析、记录校验及新实例首次读取。
磁盘模式使用宿主真实 `DomainFacility` 和 `JsonStorageBackend`，写入独立 `tmp/capacity-host-*` 目录并关闭后重开。
磁盘重开不清空操作系统页缓存，因此不冒充冷磁盘启动。

`P50/P95` 使用最近秩法并保留原始样本；只有 3 次的阶段 P95 就是最大值，不能作为总体延迟保证。
默认每组执行 3 轮恢复，每轮包含首次召回和 3 次重复召回，再重载执行同样查询；整组超时不等于单个操作超时。
内存指标包含合成备份、独立索引、严格替身、序列化对象和重载实例，不是插件独占开销。
内存重载期间原实例与新实例可能同时存活；不能据此推断宿主加载同一库的实际内存。
阶段采样堆和 RSS 可能漏掉瞬时峰值；报告额外提供子进程 `maxRSS`。
每次显式召回沿用访问强化语义，导出一致性在首次召回前验证。
睡眠聚类和模型等待不在本次容量范围内。

## E4 当时的边界

GUI 选择文件先校验实际字节数，导入和导出接口校验紧凑 JSON 大小，下载还校验格式化 JSON 的 Blob 大小，均限制 10 MiB。
测试调用 GUI 后端接口，下载边界按格式化字节数判定，不执行浏览器下载。
超限组先断言 GUI 拒绝，再使用管理工具测导出和内部可信入口测恢复；报告标为 `internal-only`。
这个测试入口不是面向用户的大文件恢复渠道，不能用内部通过声称 GUI 可用。
`maxRecords` 超限通过实际导入预演验证，拒绝后目标库必须仍为空。

首次矩阵发现大备份导出被 GUI 限制，记录在 `tmp/capacity-memory.json`。
调整测试以区分 GUI 边界和内部能力后复测，原始失败报告保留。

## 2026-11-20 实测

两套矩阵均基于 `6392816`，环境为 Windows x64、Node `v24.14.0`、AMD Ryzen AI 9 365 和约 31 GiB 内存。
每组计划 3 轮，整组限时 240 秒，子进程最大堆设置为 3072 MiB。
全量报告早于脚本指纹功能，更新后的启动器另用每组 10 条的三个场景复测通过。

## 2026-11-26 冷构建优化（E6）

E5 已补充[用户授权的大文件 v4 导入](memory-narrative-backup.md#大文件预演e5)，这里的 GUI 上限和测量结果保留 E4 原口径。
E6 以 `e1ad0ce` 的独立源码快照重跑原版矩阵，再串行运行优化版；参数仍为每组 3 轮、240 秒及 3072 MiB 堆上限。
原版的早期组运行期间还执行过定向测试和诊断，耗时与内存仍有环境波动，不作为生产延迟保证。

带 CPU 采样的 1,000 条长记录诊断中，字段分析约 2428 毫秒、签名约 26 毫秒、索引组装约 6 毫秒。
主要开销在汉字段分词和 Token 累加，因此保留签名与缓存失效逻辑，仅修改 `memory-retrieval.js`：

- 同一片段内重复汉字段按首次出现顺序分词一次，并按出现次数累计词频。
- 已有 Token 原地累加，字段合并一次写入计数；权重取最大值、词频上限及约束规则保持一致。
- 分词迭代直接收集词语，减少完整分词结果数组的临时分配。

没有持久化新索引或跨记录文本缓存；分词临时数据在当前调用结束后释放。
`varied` 样本为每条 2000 字符的不同正文，固定种子生成不同语句组合并带独立节点、路径与端口。
这组对照用于补充 E4 重复语句较多的局限，仍不能代替真实项目语料。

### 复现与语义核对

先把 `e1ad0ce` 源码放到独立目录，再分别运行基线与当前实现：

```sh
mkdir -p tmp/e6-baseline-e1ad0ce
git archive --format=tar --output=tmp/e6-baseline-e1ad0ce.tar e1ad0ce
tar -xf tmp/e6-baseline-e1ad0ce.tar -C tmp/e6-baseline-e1ad0ce
node tests/retrieval-equivalence.mjs --baseline tmp/e6-baseline-e1ad0ce
npm run bench:retrieval -- --size 1000 --profile varied --root tmp/e6-baseline-e1ad0ce --report tmp/retrieval-before.json
npm run bench:retrieval -- --size 1000 --profile varied --reference tmp/retrieval-before.json --report tmp/retrieval-after.json
```

等价核对包含 133 份记录、46 个查询和 3 种检索模式，共 18,354 项评分。
比较完整 Token、约束、索引长度和评分，覆盖原有回归与留出集、不同长正文、Unicode 及 65,536 字符连续中文。
容量报告额外保存检索源码 SHA-256；检索基准保存数据、分析与评分摘要，`--reference` 不一致时直接失败。

### 全插件容量对照

2026-11-26 原版复测 8 组通过、20,000 条长记录组超时；优化版 9 组均完成。
与 11 月 20 日相比，原版 10,000 条长记录和 20,000 条密集组这次未超时，说明耗时存在环境波动。
以下为本轮首次召回 P95（秒），每组 3 次；超时组只含已完成的调用。

| 条数 | 场景 | 原版 | 优化版 | 优化版整组耗时（秒） |
| ---: | --- | ---: | ---: | ---: |
| 1,000 | 短 | 0.235 | 0.123 | 3.03 |
| 1,000 | 长 | 2.458 | 0.158 | 4.55 |
| 1,000 | 密集 | 0.771 | 0.200 | 6.94 |
| 10,000 | 短 | 3.274 | 1.257 | 20.97 |
| 10,000 | 长 | 23.592 | 1.562 | 40.13 |
| 10,000 | 密集 | 7.989 | 2.019 | 59.12 |
| 20,000 | 短 | 4.951 | 2.314 | 43.09 |
| 20,000 | 长 | 47.122 | 3.670 | 81.66 |
| 20,000 | 密集 | 18.017 | 3.975 | 125.90 |

9 组数据摘要全部一致，完成组的重载、隔离、撤回历史及四域导出断言通过。
重复召回没有统一收益：10,000 条密集组 P95 从 0.985 秒变为 1.148 秒，20,000 条长记录从 1.271 秒变为 1.229 秒。
进程峰值 RSS 仍较高：20,000 条长记录约 3636 → 3635 MiB；包含原始备份、快照替身、独立索引与重载实例。
报告为 `tmp/e6-capacity-before.json`、`tmp/e6-capacity-after.json`；这仍是内存替身容量，不扩展真实磁盘验收规模。

### 不同正文与内存对照

最后一轮使用逐条摘要校验，原版与优化版串行交替执行，数据、Token、约束和评分摘要一致。
下表的 1,000 条耗时为三个独立进程的中位数及范围，10,000 条为单次对照，不能推断总体 P95。

| 样本 | 原版冷构建（秒） | 优化版冷构建（秒） | 进程峰值 RSS（MiB，原版 → 优化版） |
| --- | ---: | ---: | ---: |
| 1,000 条重复长正文 | 1.460（1.446～1.471） | 0.112（0.110～0.113） | 298 → 227～228 |
| 1,000 条不同长正文 | 3.318（1.737～4.225） | 2.133（1.926～2.252） | 363～375 → 370～426 |
| 10,000 条不同长正文 | 23.507 | 13.019 | 1569 → 1441 |

不同正文并非每对都更快：1,000 条第一对为 1.737 → 2.133 秒，缓存复用耗时也未稳定下降。
早期使用整数组摘要的 10,000 条对照为 23.028 → 21.563 秒，峰值 RSS 为 5737 → 5588 MiB。
该摘要会额外保留巨大的序列化字符串，已改为逐条生成相同摘要，不能将前后基准的内存差全部归因于插件优化。
两次 10,000 条优化版冷构建相差明显，因此本轮仅确认重复文本场景的显著收益及语义一致，真实不同正文还需长期观察。
最后一轮报告为 `tmp/e6-final-{long,varied}-{before,after}-{1,2,3}.json` 和 `tmp/e6-final-varied-10000-{before,after}.json`。

287 项测试、73 项 smoke、25 条确定性检索及真实宿主存储验收通过；未新增模型调用或更改持久数据格式。
